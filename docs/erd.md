# 📚 중고 도서 교환 서비스 ERD

중고 도서 교환 서비스에서 사용하는 데이터베이스 구조와 테이블 간 관계를 정리한다.

현재 도서 및 교환 요청 기능이 구현되어 있으며, 회원 기능은 추가 구현 예정이다.

---

# 1. 전체 구조

최종적으로 다음과 같은 관계를 구성한다.

```text
member
  │
  │ 1
  │
  ├──────────── N
  │              book
  │               │
  │               │ 1
  │               │
  │               └──────────── N
  │                         exchange_request
  │                                │
  │                                │ N
  └─────────────────────────────── 1
```

쉽게 표현하면 다음과 같다.

```text
회원
 ├── 여러 권의 도서를 등록할 수 있음
 │
 └── 여러 번의 교환 요청을 보낼 수 있음

도서
 └── 교환 요청을 받을 수 있음
```

---

# 2. 회원 (member)

회원 정보를 저장한다.

현재는 **구현 예정**인 테이블이다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | BIGINT | 회원 번호 (PK, 자동 증가) |
| `nickname` | VARCHAR(255) | 사용자 이름 |

회원 기능은 복잡한 로그인 시스템보다는 프로젝트에서 사용자를 구분할 수 있는 최소한의 기능으로 구현할 예정이다.

---

# 3. 도서 (book)

사용자가 등록한 도서 정보를 저장한다.

현재 구현된 테이블이다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | BIGINT | 도서 번호 (PK, 자동 증가) |
| `title` | VARCHAR(255) | 도서 제목 |
| `author` | VARCHAR(255) | 저자 |
| `description` | VARCHAR(255) | 도서 설명 |
| `status` | VARCHAR(255) | 도서 교환 상태 |

현재 도서 상태는 다음과 같다.

| 상태 | 의미 |
|---|---|
| `AVAILABLE` | 교환 가능 |
| `REQUESTED` | 교환 요청이 들어온 상태 |
| `EXCHANGED` | 교환 완료 |

회원 기능이 구현되면 다음 컬럼을 추가할 예정이다.

| 추가 예정 컬럼 | 설명 |
|---|---|
| `owner_id` | 도서를 등록한 회원 번호 (FK) |

따라서 최종적으로는 어떤 회원이 어떤 도서를 등록했는지 구분할 수 있다.

---

# 4. 교환 요청 (exchange_request)

특정 도서에 들어온 교환 요청을 저장한다.

현재 기본 기능이 구현된 테이블이다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | BIGINT | 요청 번호 (PK, 자동 증가) |
| `book_id` | BIGINT | 교환을 요청한 도서 번호 |
| `status` | VARCHAR(255) | 요청 상태 |

현재 요청 상태는 다음과 같다.

| 상태 | 의미 |
|---|---|
| `PENDING` | 교환 요청 대기 중 |
| `ACCEPTED` | 교환 요청 수락 |
| `REJECTED` | 교환 요청 거절 |

회원 기능이 구현되면 다음 컬럼을 추가할 예정이다.

| 추가 예정 컬럼 | 설명 |
|---|---|
| `requester_id` | 교환을 요청한 회원 번호 (FK) |

이를 통해 누가 교환 요청을 보냈는지 구분할 수 있다.

---

# 5. 현재 구현된 관계

현재 실제 구현 상태는 다음과 같다.

```text
book
│
│ id
│
│ 1
│
└────────────── N
          exchange_request
          │
          ├── id
          ├── book_id
          └── status
```

예를 들어:

```text
book

id      title             status
3       클라우드 입문      REQUESTED
```

3번 도서에 교환 요청이 들어오면:

```text
exchange_request

id      book_id      status
1       3            PENDING
```

형태로 저장된다.

---

# 6. 회원 기능 추가 후 관계

회원 기능이 구현되면 최종적으로 다음 구조로 확장한다.

```text
member
├── id
└── nickname
     │
     │
     ├──────────────┐
     │              │
     ▼              ▼
book             exchange_request
├── id            ├── id
├── owner_id      ├── book_id
├── title         ├── requester_id
├── author        └── status
├── description
└── status
```

관계는 다음과 같다.

| 관계 | 설명 |
|---|---|
| `member 1 : N book` | 한 회원은 여러 도서를 등록할 수 있다. |
| `member 1 : N exchange_request` | 한 회원은 여러 교환 요청을 보낼 수 있다. |
| `book 1 : N exchange_request` | 한 도서에는 여러 교환 요청이 발생할 수 있다. |

---

# 7. 최종 데이터 흐름

회원 기능까지 구현되면 다음과 같은 흐름을 표현할 수 있다.

```text
형래
 │
 │ 도서 등록
 ▼
📖 클라우드 입문
owner_id = 형래
 │
 │
 │ 교환 요청
 ▼
철수
requester_id = 철수
```

데이터베이스에서는 다음과 같이 연결된다.

```text
member
────────────────
1  형래
2  철수


book
────────────────────────────
3  클라우드 입문  owner_id=1


exchange_request
────────────────────────────
1  book_id=3  requester_id=2
```

따라서 회원 기능이 완성되면 다음 정보를 구분할 수 있다.

- 누가 도서를 등록했는가
- 누가 해당 도서에 교환을 요청했는가
- 내가 등록한 도서
- 내가 보낸 교환 요청
- 내가 받은 교환 요청

---

# 8. 구현 상태

| 테이블 / 관계 | 상태 |
|---|---|
| `book` | ✅ 구현 완료 |
| `exchange_request` | ✅ 기본 구현 완료 |
| `book → exchange_request` | ✅ 구현 완료 |
| `member` | 🔨 구현 예정 |
| `member → book` | 🔨 구현 예정 |
| `member → exchange_request` | 🔨 구현 예정 |
